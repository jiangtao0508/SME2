## 1. 一句话项目

对走 ARM SME lowering 的 Triton kernel（当前目标：FlagGems BMM）做**自动化
软件预取**：自动分析 IR → 代价模型决策（PrefetchPlan）→ 自动插入
`memref.prefetch`（最终 AArch64 `PRFM`），在不改计算（FMOPA 数量不变）的
前提下降低 cache miss、提升性能。框架目标是通用（BMM → MM → stencil），
bmm 是第一个端到端用例。

## 5. 机制理解（已确认/已推导）

### 5.1 Triton CPU program 执行

- launcher 源码：`triton-cpu/python/triton/backends/triton_shared/driver.py`
  `_generate_launcher()`（第 93 行起），生成 `_launch`：
  `#pragma omp parallel for schedule(static) num_threads(max_threads)`，
  `x=i%gridX, y=(i/gridX)%gridY, z=i/(gridX*gridY)` → kernel(x,y,z)。
- program 是"任务"（非 GPU SIMT 线程）：`schedule(static)` 按 i 连续块分给
  OpenMP 线程；线程内按 i 顺序执行；线程间并行（多核）→ 实际并发顺序不确定。
- `num_threads`：CPUOptions 默认 0 → `omp_get_max_threads()`。
- 现场 dump 的 `main.cxx` 就是这个 launcher 源码（可现场核对）。

### 5.2 SME 执行模型

- SME 是**每核心一套**（ZA 阵列 + streaming SVE 执行单元），不是全局共享。
  多线程 = 多核并行跑各自的 SME 指令流；并行度上限 = 物理核数。
- ZA/streaming mode 是 **per-thread** 状态，线程切换靠 TPIDR2_EL0 +
  `__arm_tpidr2_save/restore`（objdump 里可见）。
- kernel 入口序列：`smstart sm` → 检查/保存 caller ZA → `smstart za` →
  `zero {za}` → 计算（ld1w/mopa/st1w，16 迭代展开）→ `smstop sm`。
- **`memref.alloc` → malloc 会打断 streaming mode**（smstop→bl→smstart），
  现场 01 层需确认 alloc 是否提升出 K 循环。
- L1 每核私有、L2 视架构（Kunpeng per-core）、L3 多核共享。locality 决策：
  单核消费选 L1，跨核共享选 L2。

### 5.3 理论依据（差距已识别，不能直接套公式）

- KirbyMM（中山大学 DATE2026 outer-product BMM）：三种分块、分层 Roofline
  （L1/L2/MEM 分开）、L2/L1 组相联约束（way/set 预算）、C 流量 beta0/1。
- MPGEMM（arXiv，M4 实测）：有效工作集≠物理容量、L2 驻留约束、1Z/2Z/4Z
  带宽、L2 CMR、复用决定值不值（reuse≈mc/mr）、过滤→排序→shortlist 实测方法论。
- 差距：论文是自研 kernel（可调分块），我们是编译器固定 4x4x4（只能插预取）；
  现场调度事实（双缓冲/alloc 提升/ZA 驻留）未核实；预取参数（distance/
  locality）论文无直接模型，靠扫描实验。
- 理论文档：SME2 根目录 KirbyMM*.md、MPGEMM*.md（用户允许读，理论依据）。
